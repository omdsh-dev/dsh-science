# Agent Note: DSH Science desktop distribution and ecosystem reconnaissance

Status: proposed

English | [中文](2026-08-15-dsh-science-desktop-distribution-reconnaissance.zh.md)

## Problem

DSH Science needs one publishable v0.1 that preserves Web access, adds a normal desktop distribution, and offers Standard and Science modes without multiplying product logic. DSH already owns provider/model selection, Session persistence, permissions, settings, credentials references, and Web client composition; Science must consume those capabilities rather than create parallel stacks.

Official DSH has no desktop artifact or desktop release lifecycle, the current Science source diverges from the inspected official baseline, and required Science Session events cannot yet be registered by a purely out-of-tree bundle against that source. Community desktop and workbench projects contain useful patterns, but their age, release claims, permissions, and state models do not justify inheriting a whole fork.

The decision must also separate a v0.1 that uses existing Python/R installations from a later ordinary-user environment supply chain. Putting download, install, repair, update, rollback, or deletion into Science Runtime would mix installer authority with exact-Session execution.

## Proposal

Use one exact official DSH source baseline, a separately owned Science overlay and bundle, one shared Web client, and a thin Electron desktop host. Web and Desktop are carriers; Standard and Science are compositions. The four products share the DSH foundation rather than becoming four codebases.

Web v0.1 uses the existing HTTP/WebSocket carrier. Desktop v0.1 follows the official Client layering: Electron packages the exact DSH runtime and the same built Web client, loads that client from an app-owned `file://` entry, and provides a narrow IPC fetch/stream carrier to the Host handler. Electron owns lifecycle and transport only; it does not implement Science behavior.

Establish a new distribution baseline from exact public official source, then port the minimal generic patches and Science-owned packages. Do not rebase onto a community fork and do not preserve the present repository as a permanent whole-tree fork. The long-term target is official packages plus an out-of-tree Science bundle after the package family has public source provenance, complete integrity and compatibility identities, required downstream Session event registration, and packed-install evidence.

v0.1 does not bundle Conda or manage environments. Its Science settings card selects existing Python and R Conda environments by interpreter path and records public package-source defaults; the settings provider canonicalizes each selected interpreter to the containing Conda prefix, and the current Runtime still consumes only `pythonPrefix` and `rPrefix`, requires `conda-meta/history`, and resolves the interpreter at its fixed platform path. Arbitrary non-Conda executables are outside v0.1. A separate Science Environment Manager capability is justified only for a later one-click managed-environment release; it never belongs inside Science Runtime.

## Scope and evidence method

This decision uses read-only evidence collected on 2026-08-15. The investigation inspected repository metadata, exact commits and tags, licenses, package manifests, source, CI workflows, release metadata, and official supply-chain documentation. It did not install, execute, or trust any community plugin or binary. A broad GitHub scan reviewed 150 search results and retained 40 relevant desktop, Web UI, sidebar, artifact, workspace, and plugin-market repositories; the table below records the projects that materially affect the decision.

Repository age, stars, tags, a README statement, and the mere presence of a release are discovery signals, not maturity or security evidence. Facts below describe inspected source or metadata. Inferences explain what those facts imply. Recommendations state this project's choice.

## Baselines

### Official DSH

On 2026-08-15, the official repository's default `master` branch was [`deepseek-ai/deepseek-harness@47f943859bef60e4160492346772ded9b24f765a`](https://github.com/deepseek-ai/deepseek-harness/commit/47f943859bef60e4160492346772ded9b24f765a), committed 2026-08-13. The separately observed artifact identity is [`@deepseek-ai/dsh@0.1.0-rc.6`](https://www.npmjs.com/package/@deepseek-ai/dsh/v/0.1.0-rc.6). On 2026-08-15, [registry metadata](https://registry.npmjs.org/@deepseek-ai%2Fdsh) assigned both `latest` and `next` to RC6, recorded publication at `2026-08-13T12:35:03.812Z`, and recorded tarball integrity `sha512-brpZfED7ieRa2PQ5tUxMhHrM1pb2CmKFVM/f6yMULBDMicahk+Z2OsHgTwTDnoiZm23Ftu9rQz0NN4pflaoJcg==`; it exposed no RC6 `gitHead` and no RC5 publication timestamp. Official package publication, base-CLI installation, profile updates, and desktop updates are separate mechanisms. The exact-source [release workflow](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/.github/workflows/release.yml) publishes package tarballs from `dsh-v*` tags and assigns prereleases to `next`; the user's external npm/pnpm installation owns updates to the base `@deepseek-ai/dsh` CLI; [`dsh plugin --profile <name> update`](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/47f943859bef60e4160492346772ded9b24f765a/apps/cli/reference/README.md) only forwards to pnpm in one profile and reconciles its bundles, without updating the base CLI. This blocks package-only Science against an unchanged `47f943...` build; the unmapped RC6 artifact requires its own tarball and API audit before the same claim can be made about it.

## Web/Desktop × Standard/Science architecture

Carrier and composition are independent selections. One distribution may expose both compositions; selecting Science changes the bundle/profile and Session applicability, not the provider stack or transport protocol.

| | Standard composition | Science composition |
|---|---|---|
| Web carrier | Official Web Host/client, Standard preset and tools | Same Host/client plus Science Session, Runtime, tools, preset, settings card, chart/Outcome consumers, and provenance sidebar |
| Desktop carrier | Thin Electron host packages the exact Standard Web composition | The same Electron binary and client load the Science composition; Electron owns no Science state or execution logic |

This matrix describes composition, not platform acceptance. The current Windows sandbox reports only partial enforcement, while Science Runtime requires full enforcement for environment probes and every Python/R run; Windows Science therefore fails closed with `CONFINEMENT_UNAVAILABLE`. v0.1 may ship Windows Standard, but Windows Science is not a release target until a full-confinement provider and independent real Python/R acceptance exist. Other platforms are eligible only after their own full-sandbox and real-runtime evidence.

The shared layers are:

1. **Official DSH foundation:** Cordis, Host services, Session log and projections, permissions, provider/model capabilities, settings, credentials references, attachments, API gateway, and Web client slots.
2. **Science overlay:** Science-owned packages and a Science bundle/profile. Standard does not load Science Consumers, emit Science events, or expose Science UI.
3. **Carrier adapters:** HTTP/WebSocket for browsers and an Electron IPC fetch/stream carrier for Desktop. Both mount the same built client packages and terminate at the same Host handler. Embedding never bypasses Host permissions, credential references, origin policy, or IPC sender validation.
4. **Distribution metadata:** upstream URL/SHA/version, overlay SHA/version, bundle/profile revision, Host/client protocol identity, desktop version, package closure digest, environment identity, build provenance, checksums, signing identity, and migration range. Future accepted baseline and artifact tuples belong in dated records under [`docs/evidence/`](../../../../docs/evidence/AGENTS.md). This proposal itself records the reconnaissance identities above; no separate dated acceptance record exists, and none of these identities proves a source, package, desktop, signing, installer, or runtime PASS.

Desktop v0.1 creates one app-owned DSH Host, loads a packaged `file://` client entry, and exposes only typed fetch and stream messages through a narrow preload bridge. The main process validates the sender, top frame, entry URL, request size, response size, stream identity, cancellation, and teardown. The renderer uses context isolation, disables Node integration, denies permissions by default, rejects navigation and popups, and delegates external links to the OS. The supervisor owns single-instance behavior, tray/close policy, bounded restart, owned Host settlement, Windows child-process cleanup, and explicit-quit cleanup. The packaged runtime never falls through to an unversioned PATH DSH.

Web remains a supported product, not a development fallback. A supported client module may be embedded in another website when the embedding Host supplies the same versioned API and security policy. Arbitrary pages do not gain local filesystem, process, credential, or Science Runtime authority merely by embedding the client.

## Science environment supply

This distribution decision selects prefix-only Runtime configuration for v0.1: the settings card may present exact Python and `Rscript` pickers as discovery inputs, but each selected executable must resolve to an existing `external/unmanaged` Conda prefix. A successful settings transaction stores the derived profile prefixes and public Conda/Python/CRAN source defaults without granting install authority. v0.1 requires a Host restart before changed profile settings take effect because Runtime profiles are immutable load-time Config; the composition resolver supplies the stored prefixes to Runtime after restart. Changes affect only future Session bindings. Runtime remains the final authority that canonicalizes each prefix, requires `conda-meta/history`, resolves the fixed platform executable, and durably binds the validated identity; an existing Session binding is never rebound. The current [Science MVP product owner](../feature/2026-08-12-science-mode-core-mvp.md#v01-product-boundary) still describes optional prefixes and explicit executable configuration and must be aligned in a separate authorized product-document change before settings implementation begins. The settings card is not implemented at the investigated source identity, and DSH neither bundles Conda nor mutates a selected prefix.

A later ordinary-user one-click environment requires a separate `ScienceEnvironmentManager` capability with Service Definition, provider, and Consumers. It owns signed environment manifests, downloads, hashes, platform locks, side-by-side concrete revisions, health probes, transaction recovery, repair, rollback, and deletion of manager-owned prefixes only. Activation changes the default revision for future bindings; Runtime receives an immutable concrete prefix, never a moving alias, and remains the sole owner of exact-Session leases. Revision collection consumes Runtime settlement plus durable Session-retention pins, so an idle but retained Session does not lose the environment its provenance names.

The manager writes only manager-owned staging, cache, and revision directories; uses fixed configuration and allowed network domains; refuses disabled TLS; does not inherit user Pixi/Conda configuration, project paths, DSH home, or credential environments; and does not run package post-link scripts by default. External prefixes remain `external/unmanaged`: discovery is read-only, and import requires an explicit copy or rebuild rather than adopting, repairing, updating, or uninstalling the user's prefix. A managed manifest/revision digest must enter Runtime observation and the durable Science environment binding, while download progress and the crash-recovery journal remain manager state.

The investigation favors locked Pixi for a future managed implementation because [Pixi `v0.76.2`](https://github.com/prefix-dev/pixi/releases/tag/v0.76.2) publishes cross-platform binaries and checksums, [`pixi install --frozen/--locked`](https://pixi.sh/latest/reference/cli/pixi/install/) spans Python, R, and native dependencies, and [`pixi reinstall`](https://pixi.sh/latest/reference/cli/pixi/reinstall/) supplies a distinct rebuild operation. Checksums establish integrity, not bootstrap authenticity or channel trust. [Conda explicit specifications](https://docs.conda.io/projects/conda/en/stable/user-guide/tasks/manage-environments.html) can reproduce exact packages only on the same platform; ordinary cross-platform YAML is not an exact lock. [Micromamba](https://mamba.readthedocs.io/en/stable/user_guide/micromamba.html) is a static executable with no default Python, [uv](https://docs.astral.sh/uv/concepts/python-versions/) is Python-only and uses third-party redistributable Python builds, and [renv](https://docs.posit.co/ide/user/ide/guide/environments/r/renv.html) assumes R already exists. This is reconnaissance, not a v0.1 dependency selection or environment PASS.

v0.1 does not install or run Jupyter kernels, notebooks, or persistent kernels. A later [Jupyter Kernel Provisioner](https://jupyter-client.readthedocs.io/en/stable/provisioning.html) or kernelspec integration is an interoperability Consumer and cannot replace Runtime's exact-Session ownership; [nbformat MIME outputs](https://nbformat.readthedocs.io/en/stable/format_description.html) cannot bypass immutable attachments or chart provenance.

Private mirrors would use opaque references from the existing DSH credentials capability. A desktop credentials provider may resolve those references through [macOS Keychain](https://developer.apple.com/documentation/security/keychain-services) or [Windows Credential Manager](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritea) and inject the minimum process-scoped value; the Environment Manager never calls an OS secret store directly. Session events, manifests, logs, and subprocess diagnostics never contain the secret.

Application updates, environment updates, and data migration remain distinct. The signed desktop updater owns the packaged Node/DSH/client closure; the Environment Manager owns side-by-side environment revisions; durable Session and settings schemas migrate monotonically and transactionally with independent backup. Application rollback never silently reverses data.

## Alternatives considered

**Rebase the current history onto official upstream.** Reject. `e5e8b29...` and `47f943...` have no merge base; the left/right counts are `17/12,293`, and the downstream snapshot root is `7b9644f2b664e46c9518506035aa6c8d5af4d8e8`. A broad history replay obscures ownership and may restore conflicting branding, license, version, and release files.

**Maintain the current repository as a long-lived full fork.** Reject as the product model. It is technically feasible but makes this project own every upstream security, packaging, release, protocol, and migration change and carries the highest continuing drift cost.

**Use official npm packages plus an out-of-tree Science bundle.** Retain as the long-term target, not the current baseline. It is blocked by unmapped RC6 source provenance, complete package-family versions and integrities, Host/client/closure compatibility identity, required Science-event registration and cold replay, and anonymous packed-install evidence.

**Create a clean exact public-source baseline and port a Science overlay plus a thin Electron host.** Choose for the next distribution line. It is explicitly a `47f943...`/RC5 public-source derivative, not an RC6-equivalent build, and keeps generic candidates, Science packages, carrier code, and artifact evidence separately reviewable.

**Continue from a community desktop fork.** Reject. It inherits unowned monorepo drift, security and release decisions, days-old history, and no Science durable-state guarantee.

The chosen rebaseline procedure is:

1. Record separate `adopted_source_baseline` and `observed_artifact` identities: official URL, exact SHA, root version, source archive checksum, npm package version/integrity/source mapping, current Science identity, and every local generic/Science-owned delta. Never treat those identities as equivalent without a public mapping, and do not call a moving branch or unmapped artifact a source baseline.
2. Create a new isolated worktree at the official SHA. Do not rebase, merge, or rewrite the current Phase 3 candidate.
3. Discard downstream branding, version, license, and release configuration that conflict with the official source; preserve official notices and perform a license review.
4. Port generic fixes as independent upstreamable changes against current official APIs. Port Science Session, Runtime, tools, bundle/preset, charts/Outcome, settings, and client UI as Science-owned slices.
5. Add the thin Electron app only after the shared Web Standard and Web Science compositions pass. Keep desktop packaging and signing evidence separate from source acceptance.
6. Each official release triggers read-only intake; actual adoption occurs at a scheduled checkpoint, a blocking/security change, or v0.1 freeze. Start from the next exact public source, compare source and behavior, and replay the small owned stack. Never merge a moving `master` or unmapped npm artifact directly into a release branch.
7. ## Risks
